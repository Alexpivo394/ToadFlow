# Установка сервера

Сервер, веб-интерфейс, движок коллизий и PostgreSQL живут на одном Linux-хосте в Docker. Вся установка — это `git clone`, один файл с паролями и одна команда. Если вы хоть раз поднимали что-нибудь через `docker compose`, дальше можно читать по диагонали.

Агенты подключаются к этому хосту **сами** — открывать порты на машинах с Revit не нужно.

**На этой странице:** [что нужно](#что-нужно) · [сколько железа](#сколько-нужно-железа) · [первый запуск](#первый-запуск) · [`.env`](#переменные-env) · [выбор модулей](#выбор-модулей) · [обновление](#обновление) · [резервная копия](#резервная-копия) · [HTTPS](#https) · [логи](#логи-и-диагностика)

## Что нужно

- Linux-хост с **Docker Engine** и **Docker Compose v2** (`docker compose version`).
- Порт для веб-интерфейса, по умолчанию **8080**. К этому же адресу подключаются агенты, поэтому машины с Revit должны его видеть.
- Желательно — обратный прокси с HTTPS перед портом, см. [HTTPS](#https).
- И железо. О нём — честно и подробно.

### Сколько нужно железа

Сначала правда: значения по умолчанию в `.env.example` — движку коллизий 2 ядра и 4 ГБ, серверу 3 ГБ — это «чтобы запустилось на чём угодно», а не «чтобы работало». На хосте с 4 ядрами и 8 ГБ можно спокойно жить **без коллизий**. С коллизиями такой хост годится, чтобы проверить частный дом. Одноэтажный.

Всё решает один модуль. Выгрузке, LOI и семействам сервер почти не нужен: тяжёлую работу там делает Revit на агентах, а сервер только раздаёт задания и хранит итоги. Коллизии — другое дело: геометрию считает сам сервер.

**Куда уходит память:**

| Кто | Что ест |
|---|---|
| `clash-engine` | На время прогона держит в памяти геометрию **всей части** целиком. Главный едок |
| `server` | Разобранные слепки для наборов, 3D и картинок коллизий — по умолчанию под этот кеш уходит до половины его памяти; плюс отрисовка картинок |
| `postgres`, `web`, система | 2–4 ГБ на всех |

**Замер на настоящих моделях.** Часть из 10 моделей — 173 тыс. элементов, 69,6 млн треугольников, 60 896 коллизий в результате: пик памяти движка **6,6 ГБ**. С лимитом по умолчанию в 4 ГБ такой прогон не заканчивается — контейнер убивают по памяти посреди расчёта.

Отсюда прикидка, которой можно пользоваться: **около 1 ГБ памяти движку на каждые 10 млн треугольников части, и умножить на полтора для запаса.** Сколько треугольников в ваших моделях, видно в событии «Выгружена модель … треугольников N» после первой выгрузки.

**Ориентиры по хосту:**

| Что проверяете | Ядра | Память | Диск | В `.env` |
|---|:---:|:---:|:---:|---|
| Без коллизий: выгрузка, LOI, семейства | 4 | 8 ГБ | SSD от 50 ГБ | `MODULES=export,loi,families` |
| Коллизии, отдельное здание: части до ~100 тыс. элементов | 8 | 16 ГБ | SSD от 200 ГБ | `CLASH_ENGINE_CPUS=4` `CLASH_ENGINE_MEMORY=8g` `SERVER_MEMORY=4g` |
| Коллизии, жилой комплекс: части по 150–300 тыс. элементов, несколько проектов | 16 | 32 ГБ | SSD от 500 ГБ | `CLASH_ENGINE_CPUS=8` `CLASH_ENGINE_MEMORY=16g` `SERVER_MEMORY=8g` |
| Крупные объекты: части от 300 тыс. элементов, много проектов сразу | 24–32 | 64 ГБ | NVMe от 1 ТБ | `CLASH_ENGINE_CPUS=12` `CLASH_ENGINE_MEMORY=32g` `SERVER_MEMORY=12g` |

> [!NOTE]
> Строка про 173 тыс. элементов — замер. Остальная таблица — ориентиры, выведенные из него и из устройства движка, а не результаты нагрузочных испытаний. Берите как отправную точку и смотрите на свои цифры: `docker stats` во время прогона и **Администрирование → Сервер**.

Три вещи, которые помогают больше, чем покупка памяти:

- **Важен размер части, а не проекта.** Движок держит в памяти одну часть. Проект на двадцать корпусов, разбитый на части по корпусу, считается на скромном хосте; тот же проект одной частью — нет.
- **Ядра — это скорость, память — это «посчитается ли вообще».** Мало ядер — прогон идёт дольше. Мало памяти — прогон падает. Если выбирать, сначала память.
- **`CLASH_ENGINE_CPUS` не больше, чем ядер у хоста**, иначе контейнер не создастся вовсе. И оставьте пару ядер серверу и базе: движок на всех ядрах хоста делает веб задумчивым.

Признак, что памяти мало: прогон на большой части завершается ошибкой, а контейнер `clash-engine` перезапускается — см. [Частые проблемы → Коллизии](Troubleshooting#коллизии).

### Сколько нужно диска

Больше всего места едят слепки коллизий — один слепок большой модели может весить несколько гигабайт. Формула для прикидки:

> число моделей × размер слепка × число выгрузок за 14 дней

Слепки удачных утверждённых прогонов младше 14 дней не удаляются; остальные — по настройке «сколько последних выгрузок хранить» (**Коллизии → Параметры**). Сверх этого — база и кеш движка (до 30 ГБ). При ежедневной выгрузке это четырнадцать слепков на модель, так что диск заканчивается раньше, чем кажется. Берите SSD: движок и сервер читают слепки постоянно.

Если коллизии вам не нужны, диск скажет спасибо.

## Сервисы и тома

Четыре контейнера:

| Сервис | Что делает |
|---|---|
| `postgres` | База данных |
| `server` | API, расписания, очередь заданий, картинки коллизий |
| `clash-engine` | Движок коллизий: берёт у сервера прогоны по одному. Если модуль коллизий выключен, вежливо завершается при старте и не перезапускается |
| `web` | nginx: веб-интерфейс и прокси к серверу |

И четыре тома, в которых лежит всё ценное:

| Том | Что хранит | Жалко потерять? |
|---|---|---|
| `toadflow_postgres` | База | **Очень.** Это всё |
| `toadflow_clash` | Слепки моделей, картинки коллизий, архивы отчётов | Да, но восстановимо перевыгрузкой моделей |
| `toadflow_families` | Картинки семейств и вложения заявок. Сами файлы семейств лежат в сетевой папке библиотеки, на сервере их нет | Картинки ферма снимет заново, вложения — нет |
| `toadflow_clash-engine-cache` | Кеш слепков движка | Нет: удалите — движок скачает заново |

## Первый запуск

```bash
git clone https://github.com/Alexpivo394/ToadFlow.git toadflow
cd toadflow/deploy
cp .env.example .env
nano .env        # заполните переменные, см. ниже
docker compose up -d --build
```

Первая сборка образов занимает несколько минут — хороший повод всё-таки налить чай. Потом проверяем, что всё поднялось:

```bash
docker compose ps                          # четыре сервиса; server — healthy
curl http://localhost:8080/api/health      # {"status":"ok","db":"ok","modules":["export","loi","clash","families"],"clashVolumeFreeGb":…}
```

`/api/health` отвечает 503, если сервер не видит базу. По этому ответу Docker считает контейнер `server` здоровым; `web` и `clash-engine` стартуют только после этого.

Откройте `http://<хост>:8080` и войдите как `ADMIN_LOGIN` / `ADMIN_PASSWORD`. Дальше — [Первый запуск](Getting-started).

> [!NOTE]
> Первый администратор создаётся, только пока пользователей в базе нет. Если потом поменять `ADMIN_PASSWORD` в `.env`, пароль существующего администратора **не изменится** — его меняют в **Администрирование → Пользователи**. Это не баг, это защита от «я случайно сбросил пароль, перезапустив контейнер».

Миграции базы применяются автоматически при старте сервера.

## Переменные `.env`

| Переменная | Назначение |
|---|---|
| `POSTGRES_PASSWORD` | Пароль базы данных |
| `JWT_KEY` | Ключ подписи токенов входа, не короче 32 символов: `openssl rand -base64 48`. При смене все пользователи вылетят из системы |
| `MODULES` | Какие модули включены: `export`, `loi`, `clash`, `families` через запятую. Пусто или нет строки — все. См. [Выбор модулей](#выбор-модулей) |
| `CLASH_ENGINE_KEY` | Общий ключ сервера и движка коллизий, не короче 32 символов: `openssl rand -base64 48`. Обязателен, если коллизии включены: без него сервер не стартует |
| `ADMIN_LOGIN`, `ADMIN_PASSWORD` | Первый администратор |
| `WEB_PORT` | Порт веб-интерфейса на хосте, по умолчанию 8080 |
| `CLASH_ENGINE_CPUS` | Ядер у движка коллизий, по умолчанию 2. Не больше, чем у хоста, иначе контейнер не запустится |
| `CLASH_ENGINE_MEMORY` | Память движка, по умолчанию `4g` |
| `SERVER_MEMORY` | Память сервера, по умолчанию `3g` |
| `CLASH_IMAGE_THREADS` | Сколько картинок коллизий сервер рисует одновременно, по умолчанию 2 |
| `CLASH_ELEMENTS_CACHE_MB` | Память под разобранные слепки для наборов, 3D и картинок, МБ; `0` — половина памяти сервера |

> [!WARNING]
> В `.env.example` везде стоит `change_me`. Это не пароль, это просьба. Замените **все** такие значения, прежде чем запускать: `openssl rand -base64 48` выдаст сколько угодно хороших.

Часовой пояс расписаний, таймауты и срок хранения логов задаются уже в интерфейсе: **Администрирование → Сервер**.

## Выбор модулей

ToadFlow состоит из модулей: **выгрузка RVT / NWC** (`export`), **проверка LOI** (`loi`), **коллизии** (`clash`), **семейства** (`families`, см. [Семейства](Families)). Какие из них нужны, задаёт одна строка в `.env`:

```
# Какие модули включены: export, loi, clash, families. Пусто или нет строки — все.
MODULES=export,loi
```

Имена пишутся через запятую; регистр, пробелы и лишние запятые не важны. А вот опечатку сервер не простит: с неизвестным именем он не стартует и пишет в лог, какое имя не понял и какие допустимы. Лучше так, чем молча работать без модуля, который вы считали включённым.

**Что значит «модуль выключен»**

- Его нет в полосе слева, на «Обзоре», в списках расписаний и истории; его адреса в браузере ведут на «Обзор», а его API отвечает 404.
- Его расписания не запускаются, а задания, стоявшие в очереди при старте сервера, отменяются с пометкой «Модуль выключен».
- Контейнер `clash-engine` при выключенных коллизиях спрашивает сервер, завершается с кодом 0 и больше не поднимается; `CLASH_ENGINE_KEY` тогда не нужен.
- **Данные не удаляются.** Таблицы, расписания, части, проверки и коллизии остаются в базе.

Справочник именования моделей, источники и агенты общие и работают при любом наборе модулей.

**Как изменить набор**

```bash
cd toadflow/deploy
nano .env                 # MODULES=export,loi,clash
docker compose up -d      # пересоздаст server и clash-engine с новой переменной
```

Включили модуль обратно — всё на месте: расписания снова идут по времени, части, проверки и коллизии видны как раньше. Какие модули включены сейчас, видно в **Администрирование → Модули**.

## Вход

- Галочка **«Оставаться в системе»** на странице входа продлевает вход на 30 дней. Без неё вход заканчивается вместе с токеном входа. На общем компьютере галочку не ставят.
- Смена пароля или роли и отключение пользователя завершают все его входы.
- С одного адреса — не больше 10 попыток входа в минуту и 5 заявок на регистрацию за 10 минут; лишние получают ответ 429. Адрес клиента сервер берёт из `X-Forwarded-For`, только если запрос пришёл из частной сети: от nginx контейнера `web` или прокси в локальной сети.

## Обновление

Обычное обновление — четыре строки:

```bash
cd toadflow
git pull
cd deploy
docker compose up -d --build
```

Данные хранятся в томах и переживают пересборку контейнеров. Агенты переподключаются сами. Если вышла новая версия агента, обновите его на машинах с Revit — см. [Установка агента](Agent#обновление-и-удаление); устаревший агент помечается на странице **Ферма → Агенты**.

### С 3.1 на 3.2.0: снятие ошибок на «Обзоре»

**Править `.env` не нужно, миграций нет** — схема базы та же. Агенты и ToadTools не меняются.

1. Сделайте копию базы (привычка дешевле отката):
   ```bash
   cd toadflow/deploy
   docker compose exec -T postgres pg_dump -U toadflow toadflow | gzip > /backup/toadflow-before-3.2-$(date +%F).sql.gz
   ```
2. Получите код, соберите и запустите:
   ```bash
   cd .. && git fetch --tags && git checkout 3.2.0 && cd deploy
   docker compose up -d --build
   ```
3. Проверьте: `curl http://localhost:8080/api/health` — `"status":"ok"`; на «Обзоре» у плашки с ошибками модуля есть кнопка «Решено».

**Откат** — `git checkout 3.1.0` и `docker compose up -d --build`: база совместима в обе стороны.

**3.2.1** ставится так же — `git checkout 3.2.1`, миграций нет. После обновления у кнопки «Решено» появляется окно с примечанием, а в «Для вас» — та же кнопка у строки «расписания с ошибками». Откат на 3.2.0 — тем же способом, база не меняется.

**3.2.2** ставится так же — `git checkout 3.2.2`, миграций нет. Выпуск внутренний: в интерфейсе ничего не меняется, сервер работает и с агентами прежних версий. Новый аддин Revit приходит с установщиком агента 3.2.2. Откат на 3.2.1 — тем же способом, база не меняется.

### С 3.0 на 3.1.0: заявки, направления, уведомления

**Править `.env` не нужно.** Миграции `FamilyDirections`, `RequestsPro`, `Notifications`, `ScheduleFollowers` и `FamilySearchMisses` добавляют таблицы и поля. Данные переносятся: «срочно» прежних заявок становится «блокирует выдачу», создатели расписаний начинают следить за своими расписаниями. Агенты не меняются. Всплывающие уведомления и новые кнопки панели «Семейства» — в ToadTools 4.5.0; ToadTools 4.4 с сервером 3.1 работает как раньше.

1. Выберите окно без запусков по расписанию.
2. Сделайте копию базы:
   ```bash
   cd toadflow/deploy
   docker compose exec -T postgres pg_dump -U toadflow toadflow | gzip > /backup/toadflow-before-3.1-$(date +%F).sql.gz
   ```
3. Получите код, соберите и запустите:
   ```bash
   cd .. && git fetch --tags && git checkout 3.1.0 && cd deploy
   docker compose up -d --build
   docker compose logs server            # миграции RequestsPro… применены, ошибок нет
   ```
4. Проверьте: `curl http://localhost:8080/api/health` — `"status":"ok"`; в вебе появился колокольчик, заявки открываются, на «Обзоре» всё на месте.
5. Заведите направления BIM: **Семейства → Параметры → Направления BIM** — [Направления](Families#направления-bim). Пока их нет, заявки идут всем координаторам.

**Откат только из копии.** 3.0.1 на обновлённой базе не работает с заявками (поле «срочность» заменено). Чтобы вернуться, поднимите 3.0.1 на копии из шага 2 — как в [откате ниже](#откат).

### С 2.4 на 3.0.1: семейства и новый «Обзор»

Версия добавляет модуль «Семейства» и новый «Обзор». **Править `.env` не нужно**: строки `MODULES` нет — включены все модули, в том числе семейства; пока корень библиотеки не задан, модуль ничего не делает. Семейства не нужны — `MODULES=export,loi,clash`.

Миграции `Families`, `FamiliesSearch`, `FamiliesReadJob` и `FamiliesPanelAndRequests` только добавляют таблицы модуля; существующие данные не меняются. Новый том `families` (картинки семейств, вложения заявок) `docker compose` создаёт сам. В `deploy/nginx.conf` добавлен предел 26 МБ для вложений заявок: файл обновляется вместе с кодом, отдельно его править не нужно.

Агенты и аддин прошлых версий продолжают выполнять выгрузку, LOI и коллизии. Для семейств агент библиотеки и машины, читающие семейства, обновляются до 3.0 — см. [Установка агента](Agent#обновление-и-удаление). Панель «Семейства» в Revit — в ToadTools 4.4.0; прежние версии ToadTools работают с новым сервером.

1. Выберите окно без запусков по расписанию (или выключите расписания, которые сработают во время обновления).
2. Сделайте копию базы:
   ```bash
   cd toadflow/deploy
   docker compose exec -T postgres pg_dump -U toadflow toadflow | gzip > /backup/toadflow-before-families-$(date +%F).sql.gz
   ```
3. Получите новый код, соберите и запустите:
   ```bash
   cd .. && git fetch --tags && git checkout 3.0.1 && cd deploy
   docker compose up -d --build
   docker compose ps                     # server — healthy, clash-engine — running
   docker compose logs server            # миграции Families… применены, ошибок нет
   ```
4. Проверьте после обновления:
   - `curl http://localhost:8080/api/health` — в ответе есть `"families"`;
   - на «Обзоре» — плитка «Семейства» с надписью «папка не задана», расписания, пресеты, профили LOI, части и проверки на своих местах;
   - **Ферма → Агенты**: агенты в сети.
5. Задайте библиотеку: **Семейства → Параметры** и права на папку — [Семейства → Для администратора](Families#для-администратора).
6. Включите расписания, если выключали.

**Откат.** Версия 2.4.0 работает и на обновлённой базе: новые таблицы ей не мешают. Чтобы вернуть всё как было до обновления, поднимите 2.4.0 на копии из шага 2 — порядок такой же, как в [откате ниже](#откат).

### С 2.3 на 2.4.0: модули и новое меню

Версия меняет навигацию веба (полоса пространств вместо одного меню, «Обзор», администрирование) и добавляет выбор модулей. **Править `.env` не нужно**: строки `MODULES` нет — включены все три модуля, движок коллизий запускается как раньше. Агенты, аддин и плагины ToadTools прежних версий продолжают работать, переустанавливать их не нужно.

Миграции базы только добавляют и заполняют: столбец «модуль» у запусков (заполняется по заданиям запуска, а если заданий нет — по его расписанию) и перенос порога «агенты не в сети» из настроек коллизий в общие. Ничего не удаляется.

1. Выберите окно без запусков по расписанию (или выключите расписания, которые сработают во время обновления).
2. Сделайте копию базы:
   ```bash
   cd toadflow/deploy
   docker compose exec -T postgres pg_dump -U toadflow toadflow | gzip > /backup/toadflow-before-modules-$(date +%F).sql.gz
   ```
3. Получите новый код, соберите и запустите:
   ```bash
   cd .. && git fetch --tags && git checkout 2.4.0 && cd deploy
   docker compose up -d --build
   docker compose ps                     # server — healthy, clash-engine — running
   docker compose logs server            # миграции RunModuleName и AgentsOfflineToGeneral применены, ошибок нет
   ```
4. Проверьте после обновления:
   - `curl http://localhost:8080/api/health` — в ответе `"modules":["export","loi","clash"]`;
   - **Администрирование → Модули**: все три модуля включены, движок коллизий в сети;
   - на «Обзоре» нет строки «Движок коллизий не на связи»;
   - старые закладки (`/schedules/…`, `/history`, `/settings/users`) и ссылки из отчётов HTML (`/clash/…`) открывают нужные страницы;
   - расписания, пресеты, профили LOI, части и проверки на своих местах.
5. Включите расписания, если выключали.

**Откат.** Прежняя версия работает и на обновлённой базе: новый столбец и перенесённый порог ей не мешают. Чтобы вернуть всё как было до обновления, поднимите прежнюю версию на копии из шага 2 — порядок такой же, как в [откате ниже](#откат), с вашей версией и файлом копии.

### С 1.7.1 на 2.0.0

Версия 2.0.0 добавляет коллизии: сервис `clash-engine`, том `clash`, обязательную переменную `CLASH_ENGINE_KEY` и миграцию базы. Обратной миграции нет, поэтому сначала — копия базы.

1. Выключите в **Расписаниях** те, что сработают во время обновления.
2. Сделайте копию базы, пока сервер ещё 1.7.1:
   ```bash
   cd toadflow/deploy
   docker compose exec -T postgres pg_dump -U toadflow toadflow | gzip > /backup/toadflow-1.7.1-$(date +%F).sql.gz
   ```
3. Получите код 2.0.0 и добавьте в `.env` переменные из [таблицы](#переменные-env): обязательно `CLASH_ENGINE_KEY`, лимиты — если у хоста не 4 ядра и 8 ГБ.
   ```bash
   cd .. && git fetch --tags && git checkout 2.0.0 && cd deploy
   nano .env
   docker compose config > /dev/null    # ошибки нет — переменные заданы
   ```
4. Соберите и запустите:
   ```bash
   docker compose up -d --build
   docker compose ps                     # server — healthy, clash-engine — running
   docker compose logs server            # миграция Clash2_0 применена, ошибок нет
   ```
5. Обновите агентов до 2.0.0. Задания коллизий получают только агенты 2.0.0 и новее; агенты 1.7.1 продолжают выгружать NWC и проверять LOI.
6. Включите расписания.

### Откат

Откат возвращает код и данные на момент копии; всё, что сделано после обновления, пропадает. Пример — для возврата с 2.0.0 на 1.7.1; для других версий подставьте свой тег и свой файл копии.

```bash
cd toadflow/deploy
docker compose down
cd .. && git checkout 1.7.1 && cd deploy
docker volume rm toadflow_postgres
docker compose up -d postgres
gunzip -c /backup/toadflow-1.7.1-YYYY-MM-DD.sql.gz | docker compose exec -T postgres psql -U toadflow toadflow
docker compose up -d --build
```

Без копии 1.7.1 можно запустить на базе 2.0.0: новые таблицы и столбцы ей не мешают. Роль «Проектировщик» и заявки на регистрацию 1.7.1 не знает — до её старта их убирают:

```sql
UPDATE users SET role = 'Viewer' WHERE role = 'Designer';
DELETE FROM users WHERE is_pending;
```

Перед этим сверьте схему: таблица `users` и значения столбца `role` должны быть такими, как ожидает 1.7.1. Запись `…_Clash2_0` в `__EFMigrationsHistory` остаётся; 1.7.1 её не трогает, и при повторном обновлении миграция не выполнится второй раз.

Агентов 2.0.0 откатывать не нужно: они работают и с сервером 1.7.1.

## Резервная копия

Есть два типа администраторов: те, кто делает копии, и те, кто пока не терял базу. Будьте первым типом.

Копия — это база и том `clash`. **Сначала снимается база, потом том**: база ссылается на слепки, и в томе, снятом позже, есть все слепки, на которые она ссылается.

```bash
cd toadflow/deploy
docker compose exec -T postgres pg_dump -U toadflow toadflow | gzip > /backup/toadflow-$(date +%F).sql.gz
docker run --rm -v toadflow_clash:/d -v /backup:/b alpine tar czf /b/clash-$(date +%F).tgz --exclude=exports --exclude=uploads -C /d .
```

`exports` (готовые архивы отчётов, живут сутки) и `uploads` (недописанные загрузки агентов) в копию не входят — жалеть там нечего.

**Ежедневная копия** — две строки в `crontab -e`, и можно спать спокойно:

```text
0 3 * * * cd /opt/toadflow/deploy && docker compose exec -T postgres pg_dump -U toadflow toadflow | gzip > /backup/toadflow-$(date +\%F).sql.gz
30 3 * * * docker run --rm -v toadflow_clash:/d -v /backup:/b alpine tar czf /b/clash-$(date +\%F).tgz --exclude=exports --exclude=uploads -C /d .
```

**Восстановление** на пустые тома:

```bash
docker compose up -d postgres
gunzip -c /backup/toadflow-YYYY-MM-DD.sql.gz | docker compose exec -T postgres psql -U toadflow toadflow
docker run --rm -v toadflow_clash:/d -v /backup:/b alpine tar xzf /b/clash-YYYY-MM-DD.tgz -C /d
docker compose up -d
```

Если тома `clash` нет, не всё потеряно: коллизии и проверки сохраняются в базе, а 3D, картинки и новые прогоны ждут свежих слепков. Выгрузите модели заново — запустите расписания выгрузки для коллизий.

> [!TIP]
> Копия, из которой ни разу не восстанавливались, — это не копия, а надежда. Разверните её хоть раз на тестовой машине.

Вложения заявок на семейства лежат в томе `toadflow_families`. Если заявками пользуются всерьёз, снимайте и его — той же командой, что том `clash`, только с `toadflow_families` и без `--exclude`.

## HTTPS

Сервер отдаёт HTTP. Если интерфейс доступен за пределами доверенной сети, перед портом `WEB_PORT` ставят обратный прокси с TLS (nginx, Caddy, Traefik). От прокси нужны две вещи, и обе важные:

- пропускать `/hubs/` с WebSocket (`Upgrade` / `Connection`) и держать соединение не меньше часа: через него подключены браузеры и агенты;
- принимать тело запроса до **16 МБ**: агенты загружают слепки моделей частями по 8 МБ. nginx по умолчанию принимает 1 МБ и отвечает на большее 413.

Если пользуетесь заявками на семейства, берите лимит с запасом — **26 МБ**: вложение к заявке может весить до 25 МБ, и встроенный nginx ToadFlow пропускает именно столько.

Забудете первое — страницы перестанут обновляться сами. Забудете второе — агенты не смогут залить слепки. Оба случая есть в [Частых проблемах](Troubleshooting#сервер), потому что на эти грабли наступают все.

nginx на хосте:

```nginx
server {
    listen 443 ssl;
    server_name toadflow.example.ru;
    ssl_certificate     /etc/ssl/toadflow.crt;
    ssl_certificate_key /etc/ssl/toadflow.key;
    client_max_body_size 16m;

    location / {
        proxy_pass http://127.0.0.1:8080;
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_http_version 1.1;
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection "upgrade";
        proxy_read_timeout 3600s;
    }
}
```

Caddy:

```text
toadflow.example.ru {
    request_body {
        max_size 16MB
    }
    reverse_proxy 127.0.0.1:8080
}
```

Traefik по умолчанию размер тела не ограничивает. Если на маршруте есть middleware `buffering`, её `maxRequestBodyBytes` — не меньше `16777216`.

Агентов тогда подключают по адресу `https://toadflow.example.ru`.

## Логи и диагностика

```bash
docker compose logs -f server         # сервер: расписания, задания, подключения агентов
docker compose logs -f clash-engine   # движок коллизий: прогоны, ошибки ключа и связи с сервером
docker compose logs -f web            # nginx
docker compose restart server         # перезапуск сервера без потери данных
```

Если прогоны коллизий ждут в очереди, а движок к серверу не обращается, веб пишет «Движок не отвечает N мин» в строке прогона и на «Обзоре проверок». См. [Частые проблемы](Troubleshooting#коллизии).

## Удаление

```bash
cd toadflow/deploy
docker compose down        # остановить, данные сохранятся
docker compose down -v     # остановить и удалить базу, слепки и кеш движка
```

> [!CAUTION]
> Флаг `-v` — это «и сожги за собой всё». Он не спрашивает подтверждения. Если пальцы набрали его по привычке — у вас же есть копия, да?
