# Аналитика LOI

**Проверка LOI → Аналитика.**

Отчёт Excel отвечает на вопрос «что не заполнено в этой модели». Аналитика отвечает на вопросы поинтереснее: **становится ли лучше**, **кто отстаёт** и **какой параметр не заполняет вообще никто**.

Она показывает, как со временем заполняются параметры моделей: по заказчикам, объектам, разделам, частям здания и отдельным моделям. Видна всем пользователям, проектировщикам тоже, — пусть все видят. Настройки аналитики проектировщику и наблюдателю не видны: только смотреть.

В аналитику попадают:

- проверки LOI по расписаниям ToadFlow — если в расписании включён флажок **«Записывать итоги в аналитику ToadFlow»** (включён по умолчанию);
- ручные проверки из плагина ParamChecker координаторов и администраторов, см. [ниже](#ручные-проверки-из-paramchecker).

Хранятся только **итоги** — по модели, правилу и параметру, без самих элементов. Какие именно элементы не заполнены, показывает Excel-отчёт проверки в папке результатов расписания.

> [!NOTE]
> Не путайте эту страницу с **Проверка LOI → Настройка аналитики**: там включается аналитика и задаётся срок хранения. А [разбор имён моделей](Model-naming), по которому проверки раскладываются по объектам и разделам, — в **Ферма → Именование моделей**.

## Показатели

| Показатель | Как считается |
|---|---|
| **Заполненность** | Доля заполненных значений среди всех проверенных: заполненные / (элементы × проверяемые параметры). «Пусто» и «нет параметра» — одинаково незаполненные |
| **Полнота** | Доля элементов, у которых заполнено **всё**, что проверялось |
| **Изменение** | Разница заполненности модели с её прошлой проверкой, в процентных пунктах |
| **Моделей**, **Проверок** | Сколько разных моделей и сколько проверок попало в выборку |

Пример расчёта на четырёх стенах — на странице [Профили LOI](LOI-profiles#как-считаются-итоги).

**Светофор:** 🟢 зелёный — от 95 %, 🟡 жёлтый — от 70 %, 🔴 красный — ниже 70 %.

> [!NOTE]
> **Звёздочка `*` у изменения** значит: между проверками менялись правила профиля. Заполненность выросла на 20 пунктов со звёздочкой? Возможно, модель стала лучше. А возможно, из профиля убрали три неудобных параметра. Звёздочка не обвиняет, она просто просит не делать выводов.

### Как считается состояние объекта или раздела

Здесь три решения, и за каждым стоит здравый смысл:

- Берётся **последняя проверка каждой модели** в выбранном периоде. Модель, которую проверили десять раз, весит так же, как модель с одной проверкой. Иначе чаще всего проверяемая модель перетянула бы на себя всю статистику.
- Доли **взвешенные**: сумма заполненных значений всех моделей делится на сумму проверенных. Маленькая модель на 50 элементов не весит столько же, сколько большая на 50 000. Иначе идеально заполненная сторожевая будка спасала бы показатели всего ЖК.
- Модель, которая в периоде не проверялась ни разу, в состояние не входит.

## Фильтры

Фильтры — в строке над вкладками и действуют на все вкладки.

| Фильтр | Значения |
|---|---|
| **Период** | 30 дней, 90 дней (по умолчанию), 365 дней или всё время |
| **Заказчик**, **Объект**, **Раздел**, **Часть** | Значения из [разбора имён моделей](Model-naming) и ручных поправок. **«Не распознано»** — модели, у которых справочник это поле не нашёл |
| **Профиль** | Каким профилем проверялась модель. Профили из групп записываются с группой: «Северный · ОВ» |
| **Свои поля** | По фильтру на каждое своё поле справочника, например «Стадия: все». «Не распознано» — модели, у которых поле не нашлось |
| **Источник** | По расписанию или вручную из ParamChecker |
| **Модель** | Поиск по части имени модели |

Фильтры сохраняются в адресе страницы. Собрали срез «Северный, ОВ, стадия Р, за 30 дней» — скопируйте адрес и отправьте ГИПу. Это убедительнее, чем скриншот.

## Вкладки

### Обзор

Вид с вертолёта.

| Блок | Что показывает |
|---|---|
| Плитки сверху | Заполненность, полнота, число моделей и проверок по выборке |
| **Заполненность по дням / неделям** | Тренд. За период длиннее двух месяцев шаг — неделя |
| **По объектам**, **По разделам** | Заполненность и полнота каждого объекта и раздела |
| **Объекты × разделы** | Матрица: строки — объекты, столбцы — разделы, в ячейке — заполненность |
| **Отстающие модели** | Модели с самой низкой заполненностью |
| **Хуже всего заполненные параметры** | Параметры с самой низкой заполненностью по всем моделям выборки |

Матрица «объекты × разделы» — главный экран для планёрки: красная клетка сразу показывает, какой раздел на каком объекте отстаёт. Дальше уже вопрос не «у нас всё плохо?», а «что у ВК на Южном?».

### Модели

Все модели, проверенные в периоде: объект и раздел, часть и свои поля (например «Стадия: Р»), заполненность, полнота, изменение с прошлой проверки, когда и как проверена (по расписанию или вручную).

Кнопка **«Выгрузить в Excel (CSV)»** сохраняет таблицу файлом, который открывается в русском Excel без танцев с кодировкой и разделителями; у каждого своего поля — своя колонка.

### Параметры

Каждый проверяемый параметр по всем моделям выборки: сколько значений проверено, заполнено, пусто и где параметра нет вовсе, и в каких моделях он заполнен хуже всего.

Вкладка-диагност. Она отличает две совсем разные болезни:

- много **«пусто»** — параметр есть, его просто не заполняют. Лечится разговором с проектировщиками;
- много **«нет параметра»** — параметра нет в семействах. Лечится доработкой семейств, а проектировщики тут ни при чём.

### Страница модели

Щелчок по модели в любой таблице открывает её историю:

- полный путь к модели — под названием (его удобно скопировать для [ручной поправки](Model-naming#ручные-поправки-моделей));
- график заполненности и полноты по проверкам;
- изменение с прошлой проверки;
- правила и параметры последней проверки;
- список всех проверок: когда, кем (расписанием или пользователем), каким профилем.

## Если объекты и разделы «не распознаны»

Объект, раздел и часть здания берутся из имени модели по справочнику в **Ферма → Именование моделей**. Если в аналитике половина моделей в «не распознано» — справочник ещё не знает ваших объектов:

1. Откройте **Ферма → Именование моделей**, внизу страницы нажмите **«Модели сервиса»** и **«Разобрать»**.
2. Добавьте нераспознанные куски в справочник щелчком по ним.
3. **«Сохранить справочник»**, затем **«Пересчитать аналитику по справочнику»**.

Подробно — [Разбор имён моделей](Model-naming).

## Включить, выключить, срок хранения

**Проверка LOI → Настройка аналитики**, блок «Аналитика LOI» (меняет администратор):

| Настройка | По умолчанию | Что задаёт |
|---|---|---|
| **Сохранять итоги проверок и показывать аналитику** | включено | Выключено — новые проверки в базу не пишутся, а страница аналитики предлагает включить её. Уже записанные проверки остаются |
| **Хранить проверки, лет** | 0 — всегда | Проверки старше срока удаляются раз в сутки. Срок отдельный от срока хранения логов: смысл аналитики — длинная история |

Кроме того, в каждом расписании LOI есть флажок **«Записывать итоги в аналитику ToadFlow»**: выключите его, если проверки этого расписания в аналитику попадать не должны — например, тестовые.

Книга Excel «база для дашбордов» в расписании и в плагине ведётся **независимо** от аналитики: она пишется, даже если аналитика выключена.

## Ручные проверки из ParamChecker

Не всё обязано идти через расписания. Координатор или администратор может проверить модель у себя в ParamChecker — а итоги сами уедут в аналитику ToadFlow. Нужен ToadTools 3.4.0 или новее.

1. В Revit: **ToadTools → Подключение к ToadFlow** — адрес ToadFlow (как в браузере), логин и пароль.
2. В ParamChecker включите **«Отправлять итоги проверенных моделей в ToadFlow»**.

Дальше всё само:

- После каждой проверки итоги уходят в ToadFlow. Если сервер недоступен или ToadTools ещё не подключён, они ждут в очереди плагина и уедут позже.
- Повторная отправка проверку не задваивает.
- Проверка записывается на вошедшего пользователя, в аналитике у неё источник «вручную».

Наблюдателю и проектировщику сервер отвечает «недостаточно прав»: ParamChecker сообщает об этом и откладывает итоги в отдельную папку, ничего не удаляя.

Подробнее — [ParamChecker в вики ToadTools](https://github.com/Alexpivo394/ToadTools/wiki/ParamChecker).

## Power BI

Встроенной аналитики мало, и хочется своих дашбордов с логотипом компании? Есть два пути.

### Путь 1. Книга Excel «база для дашбордов»

Простой. В расписании LOI укажите путь к файлу `.xlsx` в поле **«База для дашбордов»** — каждая проверенная модель допишет в книгу свои итоги в том же формате, что у ParamChecker. Подключите Power BI к этой книге. Подробнее — [Расписания](Schedules#вкладка-проверка-loi).

### Путь 2. Напрямую к базе ToadFlow

Для взрослых. В базе PostgreSQL сервера есть представление `loi_analytics`: одна строка — один параметр одного правила в одной проверке.

| Колонки | Что в них |
|---|---|
| `check_id`, `checked_at`, `source` | Проверка, когда проведена (UTC), источник: `Schedule` или `Manual` |
| `customer`, `object`, `discipline`, `part` | Разрезы по справочнику именования |
| `model_name`, `model_path` | Модель |
| `profile_name`, `profile_fingerprint`, `view_name` | Профиль, отпечаток его правил (меняется при изменении правил) и вид |
| `model_elements`, `model_complete_elements`, `model_values`, `model_filled` | Итоги модели целиком |
| `rule_position`, `rule_title`, `rule_elements`, `rule_complete_elements` | Правило |
| `parameter`, `filled`, `empty`, `missing`, `total` | Параметр: заполнено, пусто, нет параметра, всего |

По умолчанию база доступна только внутри Docker. Чтобы подключить Power BI:

1. Опубликуйте порт PostgreSQL. Рядом с `docker-compose.yml` создайте `docker-compose.override.yml`:

   ```yaml
   services:
     postgres:
       ports:
         - "5432:5432"
   ```

   и выполните `docker compose up -d`. Откройте порт в межсетевом экране только для тех, кому он нужен.

2. Заведите пользователя только для чтения:

   ```bash
   docker compose exec postgres psql -U toadflow toadflow
   ```

   ```sql
   CREATE ROLE powerbi LOGIN PASSWORD 'надёжный-пароль';
   GRANT CONNECT ON DATABASE toadflow TO powerbi;
   GRANT USAGE ON SCHEMA public TO powerbi;
   GRANT SELECT ON loi_analytics TO powerbi;
   ```

3. В Power BI: **Получить данные → База данных PostgreSQL**, сервер `<хост>:5432`, база `toadflow`, пользователь `powerbi`, таблица `loi_analytics`.

Свои поля справочника (например «Стадия») — в представлении `loi_analytics_fields`: строка — одно поле одной проверки, колонки `check_id`, `field`, `value`. Свяжите его с `loi_analytics` по `check_id` и выдайте права так же: `GRANT SELECT ON loi_analytics_fields TO powerbi;`.

> [!WARNING]
> Не давайте Power BI пароль пользователя `toadflow`. Отдельная роль только для чтения — это пять строк SQL и гарантия, что чей-нибудь неудачный запрос не станет вашей проблемой.

> [!IMPORTANT]
> Заполненность в Power BI считайте так же, как ToadFlow: `SUM(filled) / SUM(total)`, а **не** средним от долей. Среднее от процентов — классическая ловушка: та самая сторожевая будка снова начнёт спасать показатели.
